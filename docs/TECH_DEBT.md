# TECH_DEBT

Актуализировано по `main` на 2026-09-03 после большого технического аудита и PR #1-#45.

Цель этого файла — хранить только реально оставшийся технический долг. Уже закрытые замечания вынесены в отдельный раздел ниже и больше не должны использоваться как список активных проблем.

## Текущий технический долг

### 1. Правила выбора турнира всё ещё распределены по нескольким слоям

- Статус: актуально, но риск снижен.
- Проблема: выбор текущего/активного/выбранного турнира по-прежнему реализуется через `tournament_service` и логику отдельных routes.
- Где находится: `app/services/tournament_service.py`, `app/routes/main.py`, `app/routes/table.py`, `app/routes/profile.py`, `app/routes/predictions.py`.
- Что уже улучшено: связанные чтения теперь могут переиспользовать один DB cursor; лишние checkout-ы устранены в MA-18.
- Почему это важно: при дальнейшем добавлении турниров правила выбора могут снова начать расходиться между страницами.
- Приоритет: medium.
- Что делать позже: постепенно свести правила выбора турнира к одному selection/context service и покрыть их единым набором тестов.

### 2. Admin-слой всё ещё крупный, хотя основной `admin.py` уже разгружен

- Статус: частично исправлено.
- Что уже сделано: `app/routes/admin.py` теперь в основном маршрутизирует запросы; значительная часть логики вынесена в `admin_actions.py`, `admin_matches.py`, `admin_tournaments.py` и сервисы.
- Что осталось: отдельные admin-модули всё ещё содержат SQL, валидацию, транзакции и бизнес-правила одновременно.
- Почему это важно: риск случайно сломать соседний admin-flow стал ниже, но не исчез.
- Приоритет: medium.
- Что делать позже: выносить операции с матчами, пользователями и титулами в узкие сервисы только по мере необходимости, без большого рефакторинга за один PR.

### 3. Главная страница всё ещё содержит заметный объём inline-JS и DOM-связанной логики

- Статус: актуально, риск снижен.
- Что уже сделано: карточки и дневные блоки частично вынесены в partial-шаблоны; главная рендерит только один месяц матчей одновременно; статические файлы теперь гарантированно синхронизируются в production.
- Что осталось: `templates/index.html` по-прежнему содержит JS для раскрытия месяцев/дней, ставок и UI-состояний.
- Почему это важно: изменение структуры HTML может затронуть клиентское поведение без ошибки на backend.
- Приоритет: medium.
- Что делать позже: выносить самостоятельные JS-блоки в модули только после появления реальной необходимости; не повторять рискованный массовый CSS/HTML split.

### 4. `templates/base.html` остаётся глобальной точкой высокой связанности

- Статус: актуально.
- Проблема: базовый шаблон управляет навигацией, tournament themes, service worker/bootstrap и частью общего поведения всех страниц.
- Почему это важно: локальная frontend-правка может повлиять сразу на весь сайт.
- Приоритет: medium.
- Что делать позже: постепенно отделять глобальный bootstrap и theme logic, сохраняя текущий DOM-контракт.

### 5. Категории качества прогнозов описаны SQL-условиями в нескольких агрегатах

- Статус: актуально.
- Проблема: правила `exact score`, `correct outcome`, `7+`, `0 points` и связанные категории вычисляются SQL-условиями в статистике/рейтингах, тогда как базовое начисление очков живёт в `app/models/scoring.py`.
- Что уже улучшено: точный счёт в профиле использует канонический `get_tournament_top_scorers()`; профильная статистика жёстко ограничена выбранным турниром.
- Почему это важно: изменение системы очков потребует проверить несколько агрегатов.
- Приоритет: medium.
- Что делать позже: зафиксировать единый декларативный контракт категорий и тестами проверять соответствие scoring/ranking/profile.

### 6. `init_db()` всё ещё содержит schema setup и legacy-safe изменения

- Статус: частично исправлено.
- Что уже сделано: введены версионированные SQL-миграции, история `schema_migrations`, checksum-и, advisory lock и автоматический запуск миграций перед production deploy.
- Что осталось: `app/db.py:init_db()` по-прежнему содержит `CREATE TABLE IF NOT EXISTS`, `ALTER`, backfill/legacy-safe операции и bootstrap данных.
- Почему это важно: остаются два механизма изменения схемы — явные миграции и старый init-путь.
- Приоритет: medium.
- Что делать позже: новые изменения схемы делать только миграциями; старые idempotent-блоки переносить/удалять постепенно после подтверждения, что они больше не нужны для bootstrap/test окружений.

### 7. Service worker cache version всё ещё задаётся вручную

- Статус: актуально.
- Проблема: версия кеша в `static/service-worker.js` не связана автоматически с release SHA/build version.
- Что уже улучшено: production deploy теперь синхронизирует весь `static/` tree byte-for-byte, поэтому серверная часть доставки ассетов надёжна.
- Почему это важно: установленный PWA-клиент теоретически может дольше держать старые ассеты, если cache version не инвалидирован.
- Приоритет: low/medium.
- Что делать позже: привязать cache namespace к release/build version либо ввести стабильную стратегию ревизий URL ассетов.

### 8. SQL всё ещё встречается непосредственно в routes

- Статус: актуально, объём постепенно уменьшается.
- Проблема: некоторые routes по-прежнему напрямую читают/изменяют `matches`, `users`, `titles`, `tournaments` и другие сущности.
- Что уже улучшено: scoring вынесен в отдельный сервис; tournament helpers умеют работать с borrowed cursor; часть admin-логики вынесена в специализированные модули и сервисы.
- Почему это важно: бизнес-правила сложнее тестировать изолированно, когда SQL и HTTP-flow находятся рядом.
- Приоритет: medium.
- Что делать позже: выносить SQL только там, где появляется повторение, сложная транзакция или реальный риск расхождения правил.

### 9. Legacy/mojibake fallback-и ещё не полностью удалены

- Статус: актуально.
- Проблема: в runtime всё ещё встречаются compatibility/normalization ветки для старых названий и битых строк; в отдельных сообщениях также остаются следы mojibake.
- Почему это важно: такие fallback-и затрудняют понимание canonical данных и могут маскировать старые проблемы кодировки.
- Приоритет: medium.
- Что делать позже: сначала проверить production-БД на реальные legacy-значения, затем исправить данные миграцией и удалять fallback-и маленькими проверяемыми PR.

### 10. Часть исключений всё ещё обрабатывается слишком широко

- Статус: актуально, но наблюдаемость значительно улучшена.
- Что уже сделано: production error context включает release SHA, request id и безопасный контекст; Telegram/health monitoring расширен; DB cleanup и многие критичные пути теперь логируют ошибки явно.
- Что осталось: отдельные широкие `except Exception` и fail-closed/fallback ветки существуют в runtime и admin-коде.
- Почему это важно: при неудачной обработке второстепенной ошибки её причина может быть менее очевидной.
- Приоритет: low/medium.
- Что делать позже: убирать молчаливое подавление исключений там, где можно добавить структурный warning без изменения пользовательского поведения.

### 11. Frontend-состояние карточки матча всё ещё частично вычисляется в Jinja/DOM

- Статус: актуально, но не критично.
- Что уже сделано: мёртвая ветка `if false and match.deadline_passed` удалена; карточки частично вынесены в home-partials; backend остаётся источником истины для разрешения/запрета сохранения прогноза.
- Что осталось: визуальные состояния строятся из нескольких Jinja-флагов и затем дополнительно меняются JS после AJAX-сохранения.
- Приоритет: low/medium.
- Что делать позже: при следующем существенном изменении карточек рассмотреть компактную Python view-model состояния, не менять текущую реализацию только ради рефакторинга.

### 12. Архитектура внешнего match sync остаётся сложнее, чем фактическая текущая эксплуатация

- Статус: низкий приоритет / legacy debt.
- Проблема: `match_service` исторически совмещает внешний API, mapping, deadline policy и persistence.
- Текущая эксплуатация: РПЛ и Кубок России ведутся вручную; старый GitHub Sync Matches workflow удалён. Поэтому прежний риск постоянного production auto-sync существенно уменьшился.
- Приоритет: low.
- Что делать позже: не рефакторить без необходимости. Если автоматический внешний sync снова станет продуктовой функцией, сначала разделить fetch/mapping/persistence и добавить явный sync summary.

## Закрытые пункты прежнего TECH_DEBT

Ниже перечислены старые замечания, которые больше не должны считаться активным долгом в прежней формулировке.

### Пересчёт очков повторялся в нескольких admin-ветках — закрыто

Теперь канонический пересчёт находится в `app/services/scoring_recalculation_service.py`; `point_service.py` является тонкой обёрткой. Пересчёт одного матча использует единый `calculate_points()`, batched update прогнозов и единый result-push outbox path.

### Результат матча мог не приводить к согласованному пересчёту points — закрыто как отдельная high-проблема

Admin result flows используют `recalc_match_points`; scoring-path централизован и покрыт тестами. Сохранённые `predictions.points` остаются материализованным результатом, но теперь это сознательная архитектура, а не набор независимых пересчётов.

### Профиль смешивал статистику разных турниров — закрыто

`get_profile_stats(user_id, tournament_id)` фильтрует агрегаты, quality rankings и последние матчи по `p.tournament_id = %s` и связывает prediction с match по tournament id.

### Проверки качества были слишком ручными — закрыто как high-проблема

После большого аудита CI блокирует критичные Ruff/runtime ошибки и известные dependency vulnerabilities; добавлены многочисленные regression/integration tests для scoring, login throttling, DB pool, migration/deploy, Web Push, backup/restore и других критичных путей. Полное style-идеальное покрытие не является обязательной целью.

### Production deploy не имел безопасных миграций/rollback/version verification — закрыто

Есть versioned migrations, immutable image verification, rollback к предыдущему образу, контроль release SHA, cleanup старых Docker images и managed control-plane sync с GitHub.

### VPS мог жить на отличающихся от GitHub control-файлах — закрыто

Production scripts/cron синхронизируются из exact release; drift контролируется `.totish-managed-release` и мониторингом.

### Статика могла не соответствовать release — закрыто

Deploy синхронизирует полный repository `static/` tree, проверяет release-файлы byte-for-byte и имеет rollback статических файлов.

### Резервные копии БД отсутствовали как независимый recovery layer — закрыто

Production создаёт PostgreSQL 17 custom-format backup, хранит daily/weekly retention, SHA-256 checksum и выполняет restore verification. 2026-09-03 ручной production drill завершился `RESTORE VERIFY OK`.

### `/health/db` был слишком дорогим и публичным — закрыто

Тяжёлые проверки кешируются/переиспользуют один DB checkout, а сам DB health endpoint ограничен внутренними callers; публичный `/health` сохранён.

### Один Gunicorn worker был single point of failure — закрыто

Production работает на двух Gunicorn workers с общей PostgreSQL-backed login rate-limit логикой; DB pool ограничен на worker.

### CI использовал другую major-версию PostgreSQL — закрыто

CI и production используют PostgreSQL 17.

### Web Push endpoint позволял потенциальный SSRF — закрыто

Push endpoints валидируются против внутренних/private адресов при сохранении и перед отправкой; redirects отключены.

### GPT analytics validator допускал quoted-identifier обход application-level фильтра — закрыто

Quoted SQL identifiers запрещены для универсального GPT analytics query; физический read-only/ACL boundary сохранён.

### Старые production/Render/GitHub Sync/OpenCode artifacts — закрыто

Неиспользуемые deploy/workflow/credential/test artifacts удалены из актуального production flow.

## Правило ведения этого файла

- Не добавлять сюда косметические пожелания без реального риска или стоимости сопровождения.
- Закрытый пункт переносить в раздел `Закрытые`, а не оставлять как активный high/medium debt.
- Приоритет `high` использовать только для дефекта, который способен повредить данные, безопасность, scoring, availability или production recovery.
- Большие рефакторинги не выполнять только ради «красоты»; для работающего production предпочтительны маленькие проверяемые изменения.
