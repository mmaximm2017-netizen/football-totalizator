## Текущий технический долг

### 1. Admin-слой всё ещё крупный

- Статус: актуально, риск снижен.
- Что уже сделано: основной `app/routes/admin.py` разгружен; логика разделена между admin-модулями и специализированными сервисами. Write-SQL для регистрации, прогнозов, титулов и жизненного цикла турниров вынесен из HTTP routes в сервисы; границы закреплены тестами.
- Что осталось: `admin_matches.py` и некоторые соседние admin-модули всё ещё крупные и совмещают HTTP-flow, валидацию и часть бизнес-логики/read-SQL.
- Приоритет: medium.
- Что делать позже: выносить узкие операции только при реальной необходимости или появлении повторения. Не делать большой рефакторинг ради размера файлов.

### 2. Главная страница всё ещё содержит заметный объём inline-JS и DOM-связанной логики

- Статус: актуально, риск снижен.
- Что уже сделано: карточки и дневные блоки частично вынесены в partial-шаблоны; root-состояние карточки теперь вычисляется Python view-model; backend остаётся источником истины для сохранения прогнозов; production static tree синхронизируется полностью.
- Что осталось: `templates/index.html` содержит клиентскую логику раскрытия месяцев/дней, ставок и мгновенного обновления UI после AJAX.
- Приоритет: medium.
- Что делать позже: выносить самостоятельные JS-блоки только при следующем существенном изменении интерфейса. Не повторять рискованный массовый frontend split.

### 3. `templates/base.html` остаётся глобальной точкой высокой связанности

- Статус: актуально.
- Проблема: базовый шаблон управляет навигацией, tournament themes, service worker/bootstrap и частью общего поведения всех страниц.
- Что уже улучшено: service worker cache namespace автоматически связан с release, поэтому ручное повышение версии кеша больше не требуется.
- Приоритет: medium.
- Что делать позже: постепенно отделять глобальный bootstrap/theme logic только небольшими проверяемыми изменениями с сохранением DOM-контракта.

### 4. Категории качества прогнозов описаны SQL-условиями в нескольких агрегатах

- Статус: актуально.
- Проблема: правила `exact score`, `correct outcome`, `7+`, `0 points` и связанные категории вычисляются SQL-условиями в статистике/рейтингах, тогда как базовое начисление очков живёт в `app/models/scoring.py`.
- Что уже улучшено: точный счёт в профиле использует канонический `get_tournament_top_scorers()`; профильная статистика ограничена выбранным турниром.
- Приоритет: medium.
- Что делать позже: если scoring будет меняться, сначала зафиксировать единый декларативный контракт категорий и regression tests. Без изменения scoring отдельный рефакторинг не обязателен.

### 5. Архитектура внешнего match sync сложнее, чем фактическая текущая эксплуатация

- Статус: legacy debt, низкий приоритет.
- Проблема: `match_service` исторически совмещает внешний API, mapping, deadline policy и persistence.
- Текущая эксплуатация: РПЛ и Кубок России ведутся вручную; старый GitHub Sync Matches workflow удалён. Поэтому этот код не является текущим production-риском.
- Приоритет: low.
- Что делать позже: не рефакторить без необходимости. Если автоматический внешний sync снова станет продуктовой функцией, сначала разделить fetch/mapping/persistence и добавить явный sync summary.

## Закрыто после предыдущей актуализации

### Выбор турнира в нескольких слоях — закрыто

PR #51 удалил старые альтернативные selection helpers. User-facing routes используют единый tournament context/selection contract, а тесты защищают от возврата параллельных правил выбора.

### `init_db()` менял схему параллельно миграциям — закрыто

PR #53 сделал versioned migrations единственным schema-bootstrap path. `init_db()` теперь только добавляет bootstrap/seed data. CI поднимает пустую PostgreSQL 17, применяет миграции, seed, импорт приложения и полный test suite. Migration `0003_bootstrap_core_schema.sql` успешно применена и на production.

### Service worker cache version задавалась вручную — закрыто

PR #48 связал cache namespace с `TOTISH_RELEASE`. Новый production release автоматически получает новый cache namespace.

### Опасный write-SQL находился непосредственно в routes — закрыто в исходной формулировке

PR #52 вынес транзакционные write-paths с реальными бизнес-правилами в сервисы, включая сохранение прогнозов с deadline protection, регистрацию/legacy password upgrade, титулы и lifecycle турниров. Простые read-only `SELECT` могут оставаться рядом с HTTP-flow и сами по себе больше не считаются активным долгом.

### Legacy/mojibake fallback-и — закрыто

PR #49 удалил подтверждённо ненужные runtime fallback-и и битые строки. Production-БД была проверена перед удалением. Тест запрещает возврат replacement character `�` в runtime-код.

### Слишком широкая обработка исключений — закрыто в исходной формулировке

PR #47 добавил точную диагностику там, где широкая обработка скрывала полезный контекст. Оставшиеся широкие исключения допустимы только как осознанные fail-closed/fallback boundaries и не считаются самостоятельным долгом без конкретного дефекта.

### Состояние match-card вычислялось одновременно в Jinja и DOM — закрыто

PR #50 перенёс каноническое root-состояние карточки (`active/closed/finished/predicted` и data flags) в Python view-model. JavaScript после успешной ставки отвечает только за мгновенное обновление уже открытой страницы.

## Ранее закрытые ключевые риски аудита

- несогласованный пересчёт points после результата матча — admin result flows используют канонический recalculation path;
- смешивание турниров в profile stats — исправлено;
- слабые CI quality gates — усилены runtime Ruff checks, dependency audit и regression/integration tests;
- небезопасные production migrations/rollback/version verification — закрыто;
- drift production host files от GitHub — закрыто;
- рассинхронизация production static tree — закрыто;
- отсутствие независимого backup/restore — закрыто, ручной backup и restore drill успешно проверены;
- дорогой публичный `/health/db` — закрыто;
- один Gunicorn worker как single point of failure — закрыто;
- несовпадение major PostgreSQL в CI и production — закрыто;
- Web Push SSRF — закрыто;
- GPT analytics quoted-identifier bypass — закрыто;
- устаревшие Render/Sync/OpenCode/deploy artifacts — удалены.

## Правила ведения TECH_DEBT

1. Не добавлять сюда косметические пожелания без реального риска, повторения или стоимости сопровождения.
2. Закрытый пункт переносить из активного списка в историю либо удалять при следующем уплотнении документа.
3. Приоритет `high` использовать только для риска потери данных, безопасности, scoring integrity, availability или recovery.
4. Не делать большие рефакторинги только ради архитектурной красоты. Предпочитать маленькие проверяемые production-safe изменения.
5. Простой read-only SQL в route, большой файл или широкий `except` сами по себе не являются долгом без конкретного риска.
