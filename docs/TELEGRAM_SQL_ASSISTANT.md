# Telegram SQL-ассистент ТОТИШ

## Возможности

Существующий host-poller принимает обычные русские сообщения и передаёт их
существующему контейнерному helper по JSON stdin. Отдельного бота, webhook,
очереди, cron или фонового опроса БД не добавлено. Действующие callback-кнопки,
карточки, уведомления и дайджест не меняют свои запросы.

Поддержаны восемь намерений: таблица, лидер, очки участника/всех участников,
последний прогноз с заданным количеством очков, точный счёт, матчи,
прогнозы, отсутствие прогнозов. Примеры доступны через /help и кнопку
«Вопросы по базе». Турнир требуется явно при первом вопросе; затем сохраняется
в контексте. РПЛ, Кубок России и ЧМ определяются по имени, неоднозначные
сезоны уточняются ID. Никакого сложения между турнирами.

Даты: сегодня, вчера, позавчера, завтра, ISO, ДД.ММ[.ГГГГ],
«17, 18 и 19 октября», «с 17 по 19 октября 2026» или
«с 17.10.2026 по 19.10.2026». Без года используется текущий год;
бот показывает выбранные даты. Даты матчей считаются в Москве.
Туры: число или порядковые слова с первого по десятый.

Имена и команды берутся из БД. Похожие написания предлагаются для
подтверждения, а не заменяются молча. Повторные встречи уточняются списком.
Контекст изолирован по паре chat/user, живёт 15 минут в памяти helper,
теряется при его перезапуске; /reset сбрасывает его. Максимум 32 контекста.
Это конечный набор правил, а не универсальное понимание русского языка.
Неподдержанные периоды и вопросы требуют уточнения или получают отказ.

## Доступ и данные

Обязательны оба условия: разрешённый `TELEGRAM_ERROR_CHAT_ID` и отправитель
`from.id == TELEGRAM_ADMIN_USER_ID`. Для callback используется `callback_query.from`,
а не автор сообщения бота. user ID не выводится из chat ID. При отсутствии
новой настройки все входящие административные команды блокируются.
Исходящие уведомления не зависят от этой настройки.

Ассистент открывает соединение через `app.gpt_db.short_gpt_read` только на
время вопроса, использует `TOTISH_GPT_DATABASE_URL`, read-only транзакцию,
таймаут подключения 5 с и SQL 10 с. В finally выполняются rollback и close.
Нового постоянного пула или keepalive нет. Основной DATABASE_URL как запасной
вариант запрещён. Подключения существующего административного меню не меняются.
Существующий warmup помощника сохранён; ассистент не добавляет startup-запросов.

Только фиксированные параметризованные SELECT из gpt_safe; endpoint произвольного
SQL не вызывается. В представлениях нет паролей, токенов, email и служебных
пользователей. Прогнозы при NULL/future deadline не видны даже агрегатам.
Поэтому ассистент до дедлайна не сообщает и отсутствие прогноза; существующая
административная карточка статуса участия сохраняется как была.

Очки берутся из сохранённого `points`, только для завершённых матчей с kickoff
не позже текущего времени. Формула и процедуры начисления не меняются.
Сортировка совпадает с ranking_service: очки, число 10+, число 7/8, число 3,
имя. Пользователи берутся из открытого gpt_safe.users: удалённые исключены и
в архивных турнирах. Поэтому архивная таблица сайта, включающая удалённых,
может отличаться. Ответ помечен как список открытых участников ТОТИШа.
Туры для ассистента вычисляются по соседним московским датам через gpt_safe.calendar_rounds, независимо от сохранённого round_number.

Не более 200 участников/матчей/строк в одном запросе; при превышении бот
явно просит сузить условия или помечает ограничение. Текст разбивается по строкам
до 3800 символов и отправляется несколькими сообщениями, без HTML/Markdown
интерпретации. Ошибки не возвращают пользователю SQL, DSN или traceback.

## Включение после отдельного разрешения на release

1. Проверить read-only `TOTISH_GPT_DATABASE_URL` в окружении контейнера и
   актуальные представления из `docs/totish_gpt_safe_schema.sql`, включая
   calendar_rounds. Миграция 0007 создаёт только новое read-only представление
   и выдаёт SELECT существующему reader; результаты и сохранённые номера не меняет.
2. Добавить в host `.env` `TELEGRAM_ADMIN_USER_ID=<реальный Telegram user ID>`.
   Оставить существующие bot token и chat ID. Никогда не выводить user ID из
   отрицательного группового chat ID и не отправлять секреты в переписку.
3. После разрешённых merge/deploy убедиться, что контейнер и host-скрипт
   соответствуют одному release. Host bot добавлен в managed-files manifest.
4. Перезапустить существующий user systemd `totish-telegram-admin.service`
   под тем пользователем, которому он принадлежит, чтобы загрузить новый код.
   Второй poller для того же токена не запускать.
5. Проверить /help, таблицу РПЛ, очки конкретного участника и закрытый прогноз;
   сверить цифры с сайтом. Проверить отказ для чужого пользователя в разрешённом
   чате. Production-проверки и перезапуск в этом PR не выполнялись.

Никаких ИИ API, ключей к моделям, новых зависимостей или обязательных платных
сервисов нет. Сохраняется обычный расход существующих VPS/PostgreSQL, в том
числе compute при пользовательских вопросах. Новых гарантий бесплатности
самого Neon или VPS этот код не создаёт.

## Проверка

`tests/test_telegram_sql_assistant.py` проверяет распознавание, даты, фильтры,
уточнения, авторизацию, дедлайны, read-only соединение и длинные ответы.
`tests/integration/test_telegram_assistant_postgres.py` исполняет реальные
SQL-шаблоны и определения safe views в изолированных временных схемах
одноразовой CI PostgreSQL через AUTO_RESULTS_TEST_DATABASE_URL; fixture
откатывает весь DDL и данные. Production DSN не используется.

## Дополнительная аналитика

Новые намерения: победы в турах, текущая серия без точного счёта,
рекорд очков за матч, сравнение двух участников, средние очки за прогноз,
число прогнозов на заданные очки или число точных счетов.

- Победа в туре: максимум суммы сохранённых очков. Все участники с одинаковым
  максимумом получают по победе; критерии общей турнирной таблицы здесь
  не применяются. Учитывается весь тур, только если каждый его матч завершён,
  имеет результат, kickoff и deadline не в будущем. Туры с некорректными/NULL
  начисленными очками исключены. Сохранённый round_number не используется. Туры совсем без
  прогнозов не дают искусственных побед. Пропуск прогноза даёт нулевой вклад.
  При отборе датами используется дата последнего матча тура в Москве.
- Серия: число последних завершённых матчей выбранной выборки до ближайшего
  результата на 10/11 очков; пропуски считаются матчами без точного счёта.
  При заданных датах/туре серия ограничена этой выборкой, что указано в ответе.
- Среднее: сумма начисленных очков / число прогнозов с начисленными очками.
  Пропуски не входят в знаменатель. Сравнение использует ту же формулу.
- Точный счёт объединяет 10 и 11; явный вопрос про 10 очков считает ровно 10.
- Рекорд относится к одному матчу, а не к сумме за тур.

Новые SELECT находятся в app/services/telegram_analytics_queries.py и используют
ту же краткоживущую read-only транзакцию, фильтры турнира и safe views.

## Правило календарных туров, согласовано 22.10.2026

Для РПЛ и Кубка каждый тур — непрерывная последовательность московских дат
с матчами данного турнира. Хотя бы один пустой день начинает следующий тур.
Нумерация с 1 по всему расписанию каждого tournament_id, включая будущие матчи,
до любых фильтров по датам/статусу. Поэтому фильтрация периода не меняет номера.
При переносах дат группировка пересчитывается; это туры ТОТИШа по датам.

Матчи категорий national_team/supercup исключены до группировки, дополнительно
исключаются команды Россия/Russia и стадии Суперкубка. NULL kickoff исключён.
Календарная классификация использует league rpl/rcup, отдельно по tournament_id.
Все запросы «в N туре», включая очки, прогнозы, сравнение и серии, выбирают матчи
через это же представление. Хранимый round_number и общая статистика вне туров
не меняются; сборная и Суперкубок продолжают входить в отчёты без фильтра тура.

В интеграционном тесте воспроизведены все согласованные пользователем 17 диапазонов
РПЛ и 6 Кубка 2026 года. Отдельно проверены московская полночь, пустой день,
исключённые матчи между датами, неверные хранимые номера, partial/future туры.
